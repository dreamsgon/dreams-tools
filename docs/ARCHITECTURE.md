# Architecture

## Runtime and identity

Standard Next.js App Router on Vercel's Node.js runtime. `next.config.ts`, `vercel.json`, package.json and the lockfile define the deployment. The old Vinext/Cloudflare Workers/Sites scaffolding and platform identity-header fallback have been removed. `proxy.ts` refreshes Supabase cookies; `lib/app-user.ts` verifies the user with Supabase Auth and rejects unconfirmed emails.

`/` is the RPG Tools home with Maptable and RPG Encyclopedia links. Both editor pages redirect unauthenticated visitors to `/account`. The token-based `/encyclopedia/player` page is public. API routes use `lib/server.ts` to authenticate and derive an owner prefix from the verified user ID, never an email or a browser-supplied owner ID. Multiple users have separate workspaces, not shared multiplayer campaigns.

## Persistence

`lib/storage.ts` implements the small bucket contract in `storage-types.ts` against private Amazon S3 using AWS Signature V4. Each user owns `MAPTABLE_S3_PREFIX/users/<encoded supabase:UUID>/`. Agent key hashes live separately under the application prefix and resolve only to an owner/campaign grant. Optional extra S3 images also include the owner prefix.

`lib/workspace-storage.ts` retains immutable workspace segments and a manifest at workspace.json as the single atomic commit point. S3 If-None-Match protects initial creation; If-Match protects later revisions. A conditional failure returns a conflict and is never retried unconditionally. No local filesystem storage is used in production.

## Large transfers

`/api/transfers` issues five-minute S3 POST policies for an exact random staging key, MIME type, and byte count. The owner prefix and purpose are server-derived/validated. Browser bytes go directly to S3; `/api/assets` and workspace writes then read the staged content under the authenticated owner's prefix. Workspace content is schema-validated before the manifest commit. Staging cannot write final workspace/settings/agent keys.

Normal JSON uses a 3 MB threshold, below Vercel's function limit. Large responses use `{downloadUrl}` with a signed private S3 GET. `lib/transfer-client.ts`, the polling loop and the MCP client follow these without cookies or bearer credentials. Image routes authenticate then redirect to a signed URL; agent image reads return a URL to avoid forwarding Authorization. Discord renders are staged before the server forwards them to a saved campaign webhook.

All temporary keys are under `MAPTABLE_S3_PREFIX/transfers/` for one-day lifecycle expiry. Failed/abandoned uploads and large-response snapshots may remain until lifecycle cleanup. Completed upload staging is removed best-effort. Immutable workspace segment garbage collection remains separate future work.

## Main code

- `components/map-app.tsx`, `board.tsx`, `map-creator.tsx`: maps, drawing and interaction.
- `lib/model.ts`, `render.ts`: validated scene/workspace types, geometry and player rendering.
- `lib/workspace-*`: saves, synchronization, conflicts and storage.
- `lib/agent-*`, `app/api/agent/*`, `scripts/maptable-mcp.mjs`: campaign-scoped map/roster access.
- `lib/rolls.ts`, `lib/dice-*`, `components/standard-dice-tray.tsx`: shared map dice, excluding character-sheet tools.
- `app/api/settings`, `discord`, `s3`, `assets`: private settings and optional integrations.
- `docs/s3-*.json`: configuration templates; these contain placeholders, not credentials.

Map data schemas are retained from the 2026-11-09 extraction. The original project was not modified. Export/import backups with embedded images to migrate; no account merging or automatic R2 transfer occurs.

## Encyclopedia

`components/encyclopedia/` and `lib/encyclopedia/` contain the imported world manager. `/api/encyclopedia/*` uses verified Supabase identities. `store.ts` stores a separate 2 MB workspace envelope with a numeric revision and S3 ETag conditional writes under each account's `encyclopedia/` prefix. Images live below that prefix and use the existing direct-upload staging service (8 MB image limit). No D1 database or Sites identity headers are required.

Hashed player/agent keys resolve to an owner and campaign, then are checked against the current campaign pointer so replacement and revocation invalidate future reads. Player responses use the original field/calendar/fog filtering. Agent keys include GM content but only the selected campaign and shared world lore. Map and encyclopedia keys are independent. Authenticated image reads redirect to five-minute signed URLs; already issued URLs remain usable until expiry.

`app/(tools)/` holds Maptable/account styles; `app/encyclopedia/` has its own layout/theme/styles. Cross-module navigation uses full page anchors to avoid global-style leakage. The encyclopedia's campaign-sync script is an explicit local export/import workflow, not automatic hosted GitHub sync.

## Campaign forum

`/forum` (`app/forum/`, its own layout and `forum.css`) is a campaign's Jcink-style roleplay forum. The address hash names the campaign: `#c-<campaign id>` for the GM's own campaign, `#m-<ref>` for one the signed-in person is a member of (the same ref as the player pages), then `&board=`, `&topic=` or `&view=`. `lib/forum/` holds it: `model.ts` (schemas, `forumRights` from the member list's forum permissions, and every change as a pure function returning the topic file to write and a change to re-apply to the forum file), `store.ts` (`users/<owner>/encyclopedia/forum/<campaign>/forum.json` plus `topics/<id>.json`, all If-Match/If-None-Match writes; the forum file is re-read and the change re-applied on a conflict, with the topic read again so a summary never goes stale), `view.ts` (what one person sees: names from the member list, character hover cards with only player-shared facts, traits and stats, links only to pages they can open) and `request.ts` (the handlers behind `POST /api/forum` and `GET /api/forum?c=&image=`, with injected deps). Pictures are limited to characters who have posted, location boards' place pages, the campaign banner and the viewer's own characters. Players post in character as characters whose Who can edit includes them; GMs and co-GMs as any character or as narrator; out-of-character boards only as yourself. Every post counts towards the member's own post count. The CSS uses the campaign theme contract's variables and class names (`.board-head`, `.category`, `.forum`, `.location`, `.topic-row`, `.post`, `.mini`…, and a `page` container) so a campaign theme can be layered on later.

Reading (`lib/forum/reader.ts`): each reader's marks live in `reads/<sha-256 of their account, 40 hex>.json` beside the forum (a "read everything up to" time plus the last post time seen per topic; a first visit starts from when they joined, the GM's from that moment). Opening a topic marks it read; Mark all as read resets the marks. `presence.json` holds when each member last opened a page (written at most once a minute per person, best effort) and the most online at once; "online" is the last 15 minutes. Turns: a topic summary's `order` lists who has posted in first-post order (characters, and `*` for the GM's narration); the one after the last poster is up, with no turn when fewer than two take part. A character is the GM's to play when no member may edit its page. The forum file's `recent` keeps three days of posts (account, character, topic, post) for Characters who posted today; the browser gets only character names, pictures and post times.

Writing: posts use the Encyclopedia's page text plus `lib/forum/markup.ts` (underline, speech, `[collapse=Title]` sections). A topic page carries `links`, the `[[page]]` targets in its posts that this reader may open, with a secret-free summary. The full reply page and edit page are hash places (`&topic=<id>&reply=1`, `&topic=<id>&edit=<post>`) that read the topic page.

Moderation: a topic summary may carry `archived`, `trashed` (`{at, by}`) and `private` (account ids besides the starter, at most 30). `canSee` hides trashed topics from everyone and private ones from all but the starter, the people named and GMs; `view.ts` builds every list, count, turn and the recent log from `shownTopics`, and the model refuses changes to topics the person can't see. Archived topics take no replies and sit in the board's archive (`&board=<id>&archive=1`). Trashed topics keep their posts and counts until deleted for good; topics more than 30 days in the Trash are deleted (10 at a time) when a moderator opens the Trash page (`&view=trash`). The browser names members for a private topic by `memberKey`, a 16-hex hash of the owner, campaign and account, which the server maps back. `bulk` applies one change per topic in turn and reports how many changed; `export` (GM only) returns a board's topics with their posts (up to 300) for the browser to turn into .html or .txt (`components/forum/forum-export.ts`); a single topic prints from the topic page it already has (`&topic=<id>&print=1`).

Masks, alerts and search: a board may carry `masks` (per group id, `read`/`start`/`reply` as yes/no/never). `boardAccess` works out each board for a member: each group's board setting, else its parent board's, else the group's forum permission; Yes in any and Never in none, as in `members.ts`; GMs (`seeGm`) and the owner aren't masked, and a subforum is unreadable when its board is. The result rides on the viewer and poster as `access`, which `canSee`, `cleanBoard` and the views read; editing a board keeps its masks and `setMasks` replaces them. Settings may hold up to three `notices`. Alerts (`lib/forum/alerts.ts`) live in `alerts/<sha-256 of the account, 40 hex>.json` beside the forum, newest first, at most 50, with a seen time: after a start or reply the server finds @names and `> — Name` quote lines among member names and character titles (a character's players, or the GM for one nobody else plays), adds a private topic's members, drops the writer and anyone who can't see the topic, and writes best effort. Search (`&view=search&q=&in=`) reads the latest 150 topics the reader can see, 10 at a time, and matches every word, case-insensitive, in titles and post text.

Board kinds: a board may carry `type` (`location`, `campaign` or `ooc`) and `width` (`full` or `half`), each kept only when it differs from the default: a board takes its category's kind (in character means location), and in character boards are full width, out of character half. `kindOf` reads the board's type before its category, so posting rules, turns and combat follow the board; `typeOf` and `widthOf` give the worked-out values for the views. Only a location keeps a `placeId`, and `editBoard` still refuses to move a board with topics between in and out of character.

AI help: forum settings may hold `ai` (`lib/forum/ai.ts`: a `connectionId` from the campaign's API-key connections, and who may use `catchUp`, `check` and `draft`), set only by `setAi` (the campaign's owner; `setSettings` keeps it). `aiFor` gives the viewer's `frame.you.ai`. The `ai` action builds a prompt from the topic as the asker sees it (`topicPage`, roll results written in, the newest posts up to about 24,000 characters) and the players' card of the character written as, and calls `Deps.ai.run`; the route's `lib/ai/forum-ai.ts` sends it with `runOnce` to that connection and adds the tokens to its monthly use. Nothing is stored except the `ai` mark on a post a moderator posts from Draft with AI.

AI apps (MCP): `lib/forum/mcp.ts` gives the hosted MCP server (`lib/mcp/load.ts`, `McpContext.forum`) the forum tools `list_boards`, `list_topics`, `read_topic`, `whose_turn`, `post_to_forum` and `start_topic`. It reads as the owner, or, when the connection has See GM-only things off, as a made-up member of the built-in Players group (their forum rights and board masks, no private topics, `readable` from `playerCampaign`). Posts go through `reply` and `startTopic` as the owner with the `ai` mark, as narration or an NPC the GM plays (`controls`), never a player-run character. The permission action `forumPosts` (Post in the forum) decides: Do it posts; Ask me keeps a reply in the topic file's `suggested` list (`suggestPost`, at most 10; the summary carries the count) for a GM or co-GM to answer with the `suggestion` action (`decideSuggestion`: approve, with the text changed or not, which rolls the dice then and posts with the `ai` mark, or skip), and puts a new topic in the AI panel like other suggestions. `fillPerms` gives connections saved before the action a setting. The recap dialog's A forum topic source turns a topic into "Player (Character): …" lines (`components/encyclopedia/recap-forum-source.tsx`).

Reports: the forum file may hold `reports` (`reportSchema`: topic, post, reporter, reason, at; at most 300, the oldest dropped). `reportPost` (anyone who can read the topic, not about their own post, one per reader per post) and `dismissReports` (moderators, all reports on a post). The request sends each moderator who can see the topic a `report` alert. `reportedPosts` limits them to topics the moderator sees; `reportsPage` (page kind `reports`) reads those topics for the post's author and a snippet. A forum address `&place=<entry>` (from a place page) goes to the board whose `placeId` is that place, with `&new=1` opening a new topic.

Pictures and emoji: the forum file may hold `uploads` (`uploadSchema`: picture id, who added it, when, `post` or `emoji`; at most 3000, 300 per member but the GM) and `emoji` (`emojiSettingsSchema`: who may use them, `all`, `staff` or `off`, and up to 200 `{code, imageId, set?}`). The request's `upload` action checks `mayUpload` (`forumPictures` for post pictures, `forumBoards` for emoji) before `deps.savePicture` (`saveStagedImage` in `lib/encyclopedia/map-images-server.ts`) moves the person's own staged transfer into the GM's Encyclopedia pictures (8 MB for posts, 256 KB for emoji, PNG, JPEG or WebP by their bytes), then `addUpload` notes it. `forumImages` lets every reader load an uploaded picture. Post markup (`markup.ts`) adds `[img=alt]<id>[/img]` and `:code:`; `checkMarkup` refuses a picture that isn't one of the forum's uploads or added by someone whose group may not add pictures, and the campaign's codes from a non-moderator when emoji are staff only (only what an edit adds is checked). The frame carries `emoji` (the list, empty when off, and whether this viewer may use them); the page kind `pictures` lists post pictures for Insert › Picture. Posts render inside `PostContext` (`forum-parts.tsx`) for the campaign key and the emoji by code.

BBCode, features, tags and maps: `postBlocks` runs `fromBbcode` first, so a post may mix BBCode and Markdown; code blocks are set aside before converting so their text stays as typed, only `https://` addresses become links, and the forum's `settings.markup` (`markdown` or `bbcode`) only picks what the toolbar writes. `[feature=<character>/<id>]Name[/feature]` and `[spell=…]` are chips: `topicPage` returns `features`, the text of each one the post names that this reader may see (`sheetOf`: the GM sees all; others need to edit the character, or a readable page with its features or spells shared with players, and never GM-only lines), and the page kind `sheet` gives Insert › Feature or spell the sheet of a character in the viewer's cast. The frame's `mentionable` (readable player characters and companions, then members who read the forum) feeds the Tag picker; alerts still come from `mentioned` in `alerts.ts`. Preset topic tags are `topicTags` on the forum (`topicTagSchema`, up to 20, set with `setTopicTags`, which also takes removed tags off topics) and `tags` on a topic summary (up to 3, from `startTopic` or `setTopic` by the starter or a moderator). Insert › Map from Maptable calls `mapScenes` and `map` (the GM, `forumPictures`): `deps.mapPicture` draws the paired campaign's scene with `scenePicture` in `players` mode and stores the JPEG with `saveMapImage`, then `addUpload` notes it like any post picture.

HTML in posts: a board's `masks` may carry `html` per group (no forum-wide permission, so it is off unless a board says Yes; `boardAccess` gives GMs `html` everywhere, and board rows carry `html` for the composer). `checkMarkup` takes the board and refuses an `[html]` part the writer adds without it; parts already in an edited post may stay. `postBlocks` sets `[html]…[/html]` aside before BBCode and Markdown and returns `{ type: "html", nodes }`, where `htmlNodes` (`lib/forum/html.ts`) has kept only allowed tags, attributes (https links, forum picture ids, colspan and similar) and inline styles checked one by one against an allow-list. `HtmlTree` in `forum-parts.tsx` builds React elements from those nodes, never `dangerouslySetInnerHTML`, inside `.post-html` (`contain: content`, so nothing leaves the post); `htmlString` writes the same tree, escaped, for downloads. `rollTags`, `emojiCodes`, `wordCount` and snippets skip or flatten HTML parts, and `pictureIds` includes their pictures.

Hover cards, profiles and post styles: the forum file may hold `card` (the GM's rows, each a style from `CARD_STYLES` and up to four field ids: `stat:<id>`, `fact:<label>`, `traits`, `role`), `strip` (which `STRIP_FIELDS` show under posts written as a character, and which are covered until hovered; `DEFAULT_STRIP` when unset) and `profiles` by account (pronouns, timezone, activity, mature, no-goes and up to four post styles). `cardValue` in `view.ts` reads one field as the viewer may see it (players never get GM-only facts, traits or hidden stats; the GM gets them marked `gm`), and `cardOf` returns designed `rows` alongside the old fields; `cardFields` and `cardSample` feed the designer. Topic posts carry `strip` from `stripOf`, and the frame carries the viewer's own `styles` for Insert › My post styles; `fillStyle` (`markup.ts`) puts the writer's text in a style's `{text}`, escaped as HTML text when the slot sits inside an `[html]` part, since those hold only HTML. Components are in `components/forum/forum-profile.tsx`.

Solo campaigns (`lib/solo.ts`): an Encyclopedia campaign may carry `solo` (the Campaigns action `solo`, or `solo` on `create`). Its player characters and companions are the owner's (`soloCharacters`): `contextOf` gives the owner them as `editable`, and `playerRunOf` counts them as player-run so MCP posts never use them. When the owner's request carries `playerView: true` (the forum's Solo bar, kept per campaign in localStorage by `forum-api.ts`), `contextOf` uses `soloPlayerRights` and the Players group's board access for a made-up member, `readable` from `playerCampaign`, and still posts as the owner; the frame's `solo` tells the browser which view it is in. Anyone else's `playerView` is ignored.

Forums are opt-in: a campaign has one when its forum file exists (`ForumStore.exists`). The Campaigns action `forum` (`lib/campaigns-server.ts`) creates an empty one with `ForumStore.create` and sets the Encyclopedia campaign's `forum` flag, which campaign rows (`BookCampaign.forum`), `hubLinks().forum` and the player view read to show Forum links without a storage call. `contextOf` in `request.ts` answers 404 with `code: "no-forum"` while the file is missing, `forumMcp` refuses the same way, and `memberships` reports `forum` only when the file exists. Forums made before this have a file and no flag; they keep working, and Set up forum leaves them as they are. The action takes an optional `setup` (`forumSetupSchema` in `lib/forum/setup.ts`), what the GM confirmed in `ForumSetupDialog`: `forumFromSetup` makes the forum file and `applyForumAccess` sets the built-in Players, Guests and Co-GMs groups' forum permissions in the member list (written only when it exists or the choices differ from the default groups). Neither runs when the forum file is already there.

Campaign themes (`lib/campaign-theme/`): `model.ts` (a theme: mode `both`/`light`/`dark`, a light and a dark colour set, fonts from `THEME_FONTS`, corners, banner `picture` or `plain`, and a stylesheet; `themeCss` turns it into variables for `.campaign-skin` plus the cleaned stylesheet; the app's own presets; `importTheme` for pasted theme code), `presets.ts` (the skins inspired by games and worlds: colours, listed fonts and CSS only, each with both versions, and `PRESET_NOTES` saying what inspired each), `skins/` (fully custom skins, one file each, which restyle every part of the forum and carry a stylesheet for each other part: `neon-wire.ts`, `citadel-station.ts`, `sword-coast.ts` and `castle-in-the-mists.ts`), `css.ts` (`cleanCss`: a small parser that writes out only what passed, every selector inside the scope, `:root`/`html`/`body` meaning the scope, no url(), @import, @font-face, `<`, backslashes, nesting or leading + and ~, `position: fixed` made absolute, keyframes renamed `skin-*`, each change reported by line) and `store.ts` (`encyclopedia/themes/<campaign>.json`, `{ live, saved }`, If-Match writes). The forum reads the file in `contextOf`, puts `liveTheme` on the frame (omitting the CSS when the browser's `theme` key matches) and handles `saveTheme`, `liveTheme` and `deleteTheme` and the `themes` page for those with `boards`. The page wraps the forum in `.skin-frame > .campaign-skin` (the frame is isolated, under the app bar and the Admin CP), and `components/forum/forum-theme.tsx` is the Admin CP, which previews its draft by compiling it in the browser and wears that theme's colours itself (`themeColours`, colours only). A theme also carries `areas` (`encyclopedia`, `maptable`, `dashboard` stylesheets; the forum's is `css`), and `themeCss(theme, scope, area)` compiles one part. Outside the forum, `components/campaign-skin.tsx` (`useCampaignSkin`) asks `/api/forum` with action `skin` for a part's live theme by campaign key (`c-<Encyclopedia campaign>`, `m-<member ref>`, or `mt-<Maptable campaign>`, found through the paired Encyclopedia campaign), keeps it per tab in session storage and sends its key back so an unchanged theme answers `same`; the page puts `.campaign-skin` on the part's own root (`.app-shell` in the Encyclopedia, `.player-layout` on player pages, which get it from `/api/encyclopedia/player-view`, Maptable's `main`, and `.hub-skin` around the dashboard), never the site's app bar. With `?skin-preview=1` the hook shows the theme the Admin CP left in local storage instead.

Dice and combat: `lib/forum/rolls.ts` reads `[roll(=label)]expr[/roll]` tags; the request handler rolls them with `secureDie` (or `Deps.random` in tests) on start, reply and edit, and the post keeps `rolls`, one per tag in order (null for a tag that isn't dice), so the browser only shows results. An edit keeps a tag's old result when its label and dice are unchanged and stamps new ones with `at`. `lib/forum/combat.ts` holds a topic summary's `combat`: `order` (slots with a name, optional `init` and the character ids `as`; none means the GM's NPCs), `round`, `turn`, `done` and an optional Maptable `source`. `reply` stamps the post with `turn` meta from the summary it read, then `afterPost` runs on the latest summary inside the store's conditional write. `setCombat` (moderators, in-character, not archived or trashed) starts, reorders, steps or ends it. `orderFromScene` reads a scene through `initiative-tracker.ts`; the route's `scenes` dep loads the owner's Maptable workspace and `campaignScenes` for the paired campaign, and `combat` with `sceneId` reads the scene on the server. A turn change sends `turn` alerts to the players of the new turn's characters, or the owner for an NPC turn.
